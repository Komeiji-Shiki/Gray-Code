## 1. MIG-02 旧存档 → manifest 模式（核实结论：已完成主路径，无需强制升级）

### 现状核实（CPF-01 已完成，代码证据）

| 检查点 | 结论 | 证据 |
|---|---|---|
| 新存档 manifest 独立存储 | ✅ | `CheckpointManifestRepository.writeManifest`（`checkpoints/cp_xxx/manifest.json`，tmp+rename 原子写）；`CheckpointManager.createCheckpoint` 只把摘要（`fileCount/backupBytes/excludedCount/manifestVersion` 等）写入会话 metadata，`fileHashes/fileStats/excluded/ignoreSnapshot` 全部进 manifest |
| 旧记录读取兼容 | ✅ | `CheckpointManifestRepository.enrichRecord`：记录已有 `fileHashes`（旧格式）→ 原样返回直接可用；无 `fileHashes`（新格式）→ `loadManifest` 回填。调用点覆盖：createCheckpoint 增量比较（CheckpointManager L428）、restore（CheckpointRestoreService L293）、保留策略合并（CheckpointRetentionService L161-162） |
| manifest 缺失时降级是否明确 | ✅ 明确 | `CheckpointRestoreService` L349-355：新格式记录（`manifestVersion` 或 `workspaceRoots` 存在）但 manifest 缺失 → 显式 `restore.manifestMissing` 错误（不按 legacy「假成功」）；真正旧格式（无 fileHashes/manifestVersion/workspaceRoots）→ legacy 路径（单根、只复制不删除） |
| 懒迁移（首次访问升级为 manifest 引用） | ✅ 已存在（读时迁移，非元数据重写） | `loadManifest(checkpointId, fallbackRecord)`：磁盘无 manifest 且有旧记录 → `buildManifestFromRecord` 生成 + best-effort 落盘 + 缓存。触发点：旧存档首次 restore / 保留策略访问。`getCheckpoints`（查询）不触发写盘（读重路径避免写放大） |

### 是否需要强制懒迁移（元数据重写）

**结论：不做，报告说明。** 计划原文是「首次访问时把旧格式记录升级为 manifest 引用」，但：

- **风险**：强制升级 = 全量重写会话 metadata（把旧记录的 `fileHashes/fileStats` 剥离、补 `manifestVersion`）。若 manifest 落盘失败或中途崩溃，旧记录被改写后原数据可能丢失；且大工作区存档的 metadata 重写是写放大。
- **无收益**：`enrichRecord` 对旧记录「原样返回」已保证所有下游可用；manifest 只是在需要时（restore/增量比较）按需生成，旧记录本身就是回退真源，双源冗余反而是安全网。
- **现状已满足**：MIG-02 的目标（旧记录可读 + manifest 缺失降级明确 + 首次访问懒生成）已全部达成。

### 本批次小补丁（1 处，MIG-02/03 交界）

`CheckpointManifestRepository.buildManifestFromRecord`：回退生成的 `ignoreSnapshot.customPatterns` 由 `record.ignorePatterns ?? []` 改为
`record.ignoreSnapshot?.customPatterns ?? record.ignorePatterns ?? []`。

理由：新格式记录（manifest 缺失场景）在写入时已把「旧 `customIgnorePatterns` + 新 `exclusion.customPatterns`」合并进 `record.ignoreSnapshot.customPatterns`，回退生成时应优先用合并快照，与快照构建口径一致；旧记录无 `ignoreSnapshot` 时回退历史字段。改动最小（1 行），不影响删除/恢复逻辑。

## 2. MIG-03 旧 `ignorePatterns` 兼容读取为新排除快照（核实结论：三处口径一致，全覆盖）

### 现状核实

「旧 `customIgnorePatterns` 合并进新 `customPatterns`」的口径在四处完全一致，均为：

```ts
[...(config.customIgnorePatterns ?? []), ...(config.exclusion?.customPatterns ?? [])]
```

| 路径 | 位置 | 用途 |
|---|---|---|
| 快照构建 | `CheckpointManager.createCheckpoint` L456-458 | `buildWorkspaceSnapshot.customIgnorePatterns`（resolver 实际生效的规则） |
| 记录/规则快照 | `CheckpointManager.createCheckpoint` L607-610 | `buildIgnoreSnapshot.customPatterns`（manifest + 记录 `ignoreSnapshot` 同一对象） |
| 恢复过滤 | `CheckpointRestoreService.createIgnoreResolver` L156-157 | 恢复目标状态裁剪（工作区侧） |
| 恢复规则对比 | `CheckpointRestoreService.buildIgnoreSnapshot` L663-665 | 当前规则 vs 快照规则差异提示 |
| 排除预览 | `webview/handlers/CheckpointHandlers.previewExclusions` L295-298 | `checkpoint.previewExclusions` 预览 |

- 合并顺序固定（旧字段在前、新字段在后）：gitignore 语义下后面的模式可覆盖前面的（含 `!` 否定），新字段能覆盖旧字段，合理。
- 恢复「备份目录侧」遍历（`includeCustomPatterns=false`）不叠加工作区配置，属刻意区分（备份目录本身位于存储根内），不是口径不一致。
- MIG-03 无需再改业务代码；`buildManifestFromRecord` 的 1 行补丁（见上）进一步保证回退路径也使用合并后的快照。

## 3. MIG-04 迁移版本号 + 失败回滚 + 可恢复中间状态（已实现）

### 新增/修改文件

- **新建 `backend/modules/conversation/branch/BranchMigration.ts`**
  - 迁移注册表：`Map<fromVersion, step>`；`registerBranchMigration(fromVersion, step)`（重复注册拒绝）、`unregisterBranchMigration`（测试/热更新）、`getRegisteredBranchMigrationSteps`、`getCurrentBranchGraphVersion`（= `BRANCH_GRAPH_VERSION`）。
  - `migrateBranchGraph(graph, { targetVersion? })`：
    - 链式逐版本升级（v → v+1 → … → target，默认当前版本）；每个 step 返回后框架强制 `version = v+1`（step 无需自理版本号）；
    - 幂等：已是最新 → 原样返回 `{ migrated: false }`；
    - 未知版本拒绝：version 非正整数、高于目标版本（未来版本）→ 抛 `BranchError('BRANCH_STORAGE_CORRUPT')`，绝不猜测式降级；
    - 失败回滚：升级前对输入图深拷贝（JSON 备份）+ 每步前再备份中间态；step 抛错时恢复备份并抛 `BRANCH_STORAGE_CORRUPT`（内存内未落盘，等于恢复原版本；调用方可重试或降级线性模式）。
  - 可恢复中间状态：未来新增 v2→v3 只注册新 step，存量 v1 图仍可 v1→v2→v3 链式升到最新。
- **修改 `BranchGraphRepository.ts`**
  - 抽出私有 `writeGraphFile`（tmp+rename 原子写）；`save` 与新增 `migrate` 都包在 `runWriteSerialized` 内（避免 migrate 内嵌套 save 造成写队列自等死锁）。
  - 新增 `migrate(conversationId, { targetVersion? })`：无 sidecar → no-op；损坏 → 抛 `BRANCH_STORAGE_CORRUPT` 且不覆盖原文件；版本落后 → 迁移 + 原子保存；已最新 → 不重写。
- **修改 `branch/index.ts`**：导出 `BranchMigration`。

### 测试（`backend/__tests__/conversation/branchMigration.test.ts`，15 用例全绿）

- v1→v2 单步迁移（version 覆写 + 输入不被修改）；v1→v3 链式升级；
- 幂等（已最新原样返回）；
- 未知版本拒绝：未来版本（99）、非正整数（0/-1/1.5/NaN）、缺失步骤 → 全部 `BRANCH_STORAGE_CORRUPT`；
- 失败回滚：step 抛错 → 抛错码正确 + 输入图深比较不变；链式第二步失败时第一步中间结果不泄漏；
- 重复注册拒绝 / unregister 生效；
- `BranchGraphRepository.migrate` 集成：落盘升级 + 原子写无 tmp 残留、无 sidecar no-op、损坏不覆盖、已最新不重写。

## 4. MIG-05 完整性检查工具（已实现，纯函数模块 + 测试；命令入口后续接）

### 新增文件

- **`backend/tools/maintenance/integrityCheck.ts`**（纯只读，不依赖 vscode/ConversationManager/CheckpointManager 实例，运行时仅 node fs）
  - `checkHistoryIntegrity(baseDir, conversationId)`：segmented index 与段文件一致
    - `Σsegments.count === totalMessages`（HISTORY_SEGMENT_COUNT_MISMATCH）；
    - 段齐全（索引引用的段文件存在，HISTORY_SEGMENT_FILE_MISSING）、连续无缺口（HISTORY_SEGMENT_GAP / RANGE_INCONSISTENT）；
    - 段文件行数与 count 匹配（HISTORY_SEGMENT_LINE_COUNT_MISMATCH）；
    - 孤儿段文件（HISTORY_ORPHAN_SEGMENT，warning）；index 损坏（HISTORY_INDEX_CORRUPT）；
    - 无 segmented index（legacy/空会话）→ 跳过不报告。
  - `checkCheckpointIntegrity(checkpointsDir, records)`：记录 vs 备份目录/manifest/增量链
    - `backupDir` 存在（CHECKPOINT_BACKUP_DIR_MISSING）且为合法目录名（复用 `isSafeCheckpointDirName`，CHECKPOINT_BACKUP_DIR_UNSAFE）；
    - manifest 可解析（CHECKPOINT_MANIFEST_CORRUPT / INVALID_SHAPE）、`checkpointId` 匹配（ID_MISMATCH）；
    - 新格式记录 manifest 缺失 → error（CHECKPOINT_MANIFEST_MISSING，数据丢失）；旧格式 → warning（CHECKPOINT_MANIFEST_MISSING_LEGACY，可回退生成）；
    - 增量链 `baseCheckpointId` 引用存在（CHECKPOINT_BASE_MISSING）+ 无环（CHECKPOINT_CHAIN_CYCLE）。
  - `checkBranchIntegrity({ baseDir, conversationId, historyIds?, branchValidator? })`：
    - branches.json 解析/结构（BRANCH_JSON_CORRUPT）；图结构 `validate`（含 exportedFrom/exportedRefs 引用存在性，映射为 BRANCH_* 码）；
    - 活跃路径 vs 主历史 id 链：默认内置只读轻量比较（读分段文件消息 id，过滤 functionResponse，决策 8）；**也可注入 `branchValidator` 复用 `BranchService.validateActivePathMatchesHistory`**（提供时跳过内置比较避免重复报告）。
  - `runIntegrityCheck({ baseDir, checkpointsDir, conversationIds?, getCheckpointRecords?, branchValidator? })`：全量编排（枚举 conversations 目录 / 限定列表；存档记录默认读 `{id}.meta.json` 的 `custom.checkpoints`，与 `CheckpointQueryService` 同源），输出结构化报告：`summary{ totalIssues, errors, warnings, byScope }` + 每类 `{ checked, byCode(每类问题计数), issues(清单即示例) }`。
  - 辅助：`listConversationIds` / `readCheckpointRecordsFromMeta` / `readHistoryIdsFromSegments`。
- **`backend/tools/maintenance/index.ts`**：导出 + 后续命令入口接线说明（baseDir=StoragePathManager 有效数据路径、checkpointsDir、branchValidator=getGlobalBranchService()…）。
