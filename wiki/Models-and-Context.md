# 模型、图片与上下文

[返回目录](Home.md)

本章介绍 GrayCode 的模型渠道协议支持、上下文优化、Prompt Caching 保持机制以及视觉模型配置。

---

## 1. 模型渠道与协议适配

GrayCode 原生支持主流大模型协议，并在协议层做了深度适配：

启用渠道的自动重试后，连接失败、网络超时和网关故障依次等待 5 分钟、15 分钟、30 分钟各重试一次，最多补试三次；每段等待从上一次失败时开始计算，等待期间可以停止任务。普通 API 错误与空回复继续使用配置的重试次数和间隔，限流继续遵守上游的 `Retry-After`。已经显示正文、发出工具调用或发送原生连接请求后，沿用现有的中断处理，避免重复执行。

| 协议类型 | 适用渠道 / 服务商 | 工具调用与多模态特点 |
| --- | --- | --- |
| **OpenAI Chat Completions** | DeepSeek、SiliconFlow、OneAPI、Moonshot 等 | 标准 `tool_calls` 与兼容格式，多模态通过标准 `image_url` 传入 |
| **OpenAI Responses** | OpenAI 官方最新 Responses 接口 | 采用原生输入块结构，保留 reasoning 密文与 assistant 的 `phase`、item 边界，支持结构化与多模态流式响应 |
| **Anthropic** | Claude 系列模型 | 官方 Content Blocks（含 tool_use / tool_result 与原生多模态传递） |
| **Gemini** | Google Gemini 系列多模态模型 | 原生多模态部件与 Function Calling 格式 |

Responses 默认显式发送工具 `strict: false`，保留工具声明中可选参数的语义，避免上游自动严格化后把初次调用的 `cursor` 等参数变成必填。显式启用严格工具模式时，会把可选参数转换为可接受 `null` 的严格 schema；运行器按原声明解释省略值，不要求模型编造占位参数。切换该设置或升级工具声明会改变工具请求前缀，首次请求的缓存命中率可能降低。

Responses 的 assistant 输出按原生 item 保存并回放；`phase` 只采用上游实际返回值，不为旧历史猜测阶段。流末的 `completed` / `incomplete` 输出用于校准已接收的增量并补齐元数据，不会把同一正文或工具调用再次追加。

## 2. Prompt Caching（提示词缓存）与上下文稳定性

大语言模型的 Prompt Caching 能大幅降低长上下文对话的延迟与 API 费用。GrayCode 在架构设计上高度注重前缀稳定性：

- **确定性请求前缀**：系统提示词（System Prompt）、工具声明（Tool Declarations）和历史消息按稳定顺序组装。
- **追加式交互**：新产生的工具调用结果、截图和用户输入均追加在末尾，不会在会话中途随意重排历史项，确保尽可能多地命中服务商的 Prompt Cache（如 Claude Caching、DeepSeek 缓存）。
- **增量读取**：前端和执行器交互采用增量游标同步历史，避免频繁重复序列化庞大的历史记录。
- **运行中追加输入**：独立桌面/Web 的忙时输入会保存文字和附件，在下一次模型调用边界交付，当前任务继续运行。等待交付的消息持续显示在输入框上方，可编辑正文和附件或撤回；切回对话或刷新页面会重新读取。消息被模型取走，或原生连接确认接收后，从候选区移除；编辑、撤回与交付同时发生时，以服务端实际结果为准。发送失败保留草稿，重试沿用同一消息身份。显式队列与旧扩展行为保持原有规则，连续追加沿用现有频率和待处理数量设置。运行内插话、提问回答及后台反馈不改变本次动态上下文的插入锚点；只有正常开始的新回合建立新锚点。这不改变追加输入的用户角色或指令语义。
- **停止后的输入**：任务停止后到达的输入保留在历史中，用户手动继续时再处理。
- **上下文处理方式**：手动总结和自动处理都优先使用当前模型渠道的方式；渠道未单独设置时，沿用 **设置 → 总结设置** 的默认值。阈值只控制自动触发。手动总结等待期间可以切换对话、打开设置或取消总结，完成后只更新发起总结的会话。
- **用户原文保留**：在 **设置 → 总结设置** 中选择普通会话保留“首条用户消息＋最近一次输入”（默认）或“全部用户消息”。两种策略都始终保留切换前最近一次真实用户输入，包括运行中插话或对工具提问的回答；工具结果、内部提醒、后台任务通知不算用户输入。自动/手动普通总结和笔记管理共用此策略，Bot 继续使用自己的规则。设置在后续回合或手动操作时生效；原文与附件不被改写，恢复边界或切换分支时重新计算覆盖关系。
- **笔记管理**：选择 `notes` 方式后，先用 `context_notes` 保存工作笔记，再用 `new_context` 切换到新的上下文继续任务。连续切换时按原始消息身份保留最近一次用户输入。工作笔记也可独立保存和读取。
- **关联笔记**：模型可以用 `context_notes(record)` 在工作过程中批量记录有来源的约束、决定、观察、推测、任务和经验，关联依赖、适用对象、冲突与替代关系。每条记录引用本会话原消息，可附唯一的逐字摘录。记录跟随当前历史分支，保留生效时间与记录时间；普通自由笔记的保存与读取方式不变。
- **按任务召回**：`context_notes(recall)` 根据当前问题或任务笔记 ID 查找相关依据，需要明确提供 `tokenBudget`（256–16000，本地估算，包含引用等返回内容）。当前可见上下文中已经记录、召回或逐字出现的内容只返回短引用；换窗口后可以重新读取。`inspect` 可按 `noteId` 明确重看正文，`context_history(read)` 继续读取原始证据。返回的 `truncated`、`omitted`、`unavailable` 和 `missingDependencies` 提示哪些依据尚未完整提供。

笔记结果卡片直接展示本次记录的正文、来源与关系；召回结果区分新返回正文、已经提供的依据、缺失依赖和省略原因，并显示本地估算 token 与预算。明确重读会显示笔记状态和续读偏移，记录成功或正文已在上下文中提供时不会再被误报为“没有条目”。
- **决定更新与缓存**：新决定通过 `supersedes` 引用原决定，查询会沿关系找到当前有效版本；原工具结果保持原样，新内容仅追加。图查询不会自动把笔记全文写进每轮系统提示，也不会为整理关系额外调用模型。新版本的工具说明需要首次重新处理，可在新会话或正常切换上下文时启用；之后笔记更新不会回写已发送的前缀。
- **查询用量**：`context_status` 查询当前 token 用量与总结策略。结果卡显示输入用量、进度、剩余额度、预留输出和管理方式，明细与原始数据按需展开。数值为系统提示、工具定义及活跃历史的本地估算，统计范围截至查询前，供容量规划参考。
- **历史定位与分页**：`context_history(search)` 返回命中附近片段及 UTF-16 `matchOffset` / `previewStartOffset`，可直接作为 `read.offset`。读取历史和笔记用 `nextOffset` 续查；历史列表/搜索则用 `nextBeforeId`，每页最多 50 条。笔记目录显示更新时间和字符数，按最近更新排序。
- **排查缓存下降**：对比完整上游请求的工具、instructions、input（包括 reasoning 密文和 message 元数据）及缓存相关参数，不能仅凭扁平聊天日志判断 reasoning 是否丢失。前缀稳定是本地能控制的条件，并不保证上游命中；即使请求前缀未变，路由、缓存保留状态等也需要服务商侧证据，不能据此直接认定本地消息被改写。

## 3. 工作区上下文自动注入

在每次向模型发送指令时，GrayCode 可以在系统上下文中自动附带当前工作区的精简状态，以便模型快速感知工程全貌：

进入 **设置 → 上下文（Context）** 可自定义注入策略：

- **文件树深度**：控制自动附带的目录树层级（默认深度 2，深层代码按需通过搜索工具探索）。
- **打开的标签页列表**：告知模型当前用户正在编辑或查看哪些文件。
- **工作区诊断（LSP 错误与警告）**：将当前打开文件中的语法错误、类型检查警告智能摘录进上下文，方便模型针对性修复问题。

## 4. 视觉模型与媒体预处理

GrayCode 支持向多模态模型发送本地图片、剪贴板截图以及 PDF 文档。

### DeepSeek Vision 专属预处理
针对 DeepSeek 等对图像分辨率、格式或长图有特殊要求的视觉模型，可在渠道设置中开启 **DeepSeek Vision 预处理**：
- **PDF 逐页渲染**：借助 `pdfjs-dist` 与 `@napi-rs/canvas`，将 PDF 逐页高精度栅格化为多模态图片发送，保留原始排版与图表。
- **GIF 动画拆帧**：自动将动态 GIF 采样为多帧序列图片，确保模型能观察到动图中的连续变化。
- **格式规范化**：自动将各类格式（如 WEBP/AVIF/TIFF/BMP 等）无缝转码为官方推荐的图像格式。
- **尺寸自适应**：在保留关键细节的前提下等比例适配至推荐像素预算，避免因超大分辨率被拒收。

> 相关可选依赖可在桌面的 **依赖管理** 面板中一键安装或更新。

## 原生 Responses WebSocket 与异步工具

在 OpenAI Responses 渠道设置中，可以分别开启“原生 WebSocket 与生成中补充消息”和“原生异步工具”。两项默认关闭，旧配置继续使用原来的 HTTP 请求。独立桌面与 Web 平台使用这些能力；上游模型和中转网关也必须支持对应的 Responses 功能。原生异步也可使用流式 HTTP，无需同时开启 WebSocket。

WebSocket 在一次任务内复用同一个连接。后续请求使用当前连接的响应 ID，只发送新增输入；切换或压缩历史后会用完整上下文开始新的响应。会话缓存标识、历史图片、推理签名和模型输出的阶段信息继续保留。

生成中发送的补充消息先保存到本地，再提交给上游。上游确认排队后，GrayCode 等待自动续接或所需工具结果，不会把同一条消息再发送一遍。原回复与续接回复分别保存在历史中；上游明确拒绝该补充时，消息转为下一次普通输入。断线导致发送结果不确定时，任务会报告连接错误，已保存的消息仍可查看。

原生异步将独立读取、语言服务查询、`execute_command` 和浏览器工具声明为 `async: true`。模型为每次调用填写会话中唯一的 `task_handle`，收到完整参数后，运行器按原权限、审核和确认规则执行，最多同时执行 4 个。待完成的调用可跨越多次模型请求；已经完成的结果通过原始 `call_id` 返回，Responses 返回的工具命名空间也随调用历史保留。模型用 `wait_for_tasks` 的 `task_handles` 只等待所需任务，结果先于等待回执进入下一次请求。如果模型已无其他工作，运行器等待任务进展后再继续，不循环请求模型。待完成期间，自动总结和上下文切换推迟到结果配对后。

同一 Responses 任务在 HTTP/SSE 与 WebSocket 中都检查账户、端点和模型身份，避免在继续回放原生调用或推理密文时混用不同身份；同一订阅账户的令牌刷新继续允许。工具目录在任务开始时捕获，通用异步等待说明集中在等待工具中，后续请求沿用相同目录。工具声明的这次调整会使升级后的固定请求前缀改变一次，已有历史和图片顺序保持不变。

`execute_command` 的 `background=true` 在原生异步模式下返回最终输出和退出码，沿用原终端任务的状态、输出和停止入口，完成时不重复发送普通后台通知。取消当前生成仍保留已启动的后台命令，结果由持久反馈队列交付。服务重启仅恢复已保存的终态，未完成操作标记中断，不自动重放。常驻开发服务器应使用 `run_command` 获取进程会话，避免等待服务退出。

浏览器导航、观察、条件等待、点击、输入和文件传输使用相同的异步调用机制。同一标签页仍按原队列执行，不同标签页可以并行；模型必须等待最新截图或快照后，才能使用其观察 ID 或元素引用进行依赖该结果的操作。人工接管和取消规则保持原样。

开启后，工具声明增加任务句柄与等待工具，首次启用或升级会改变模型请求的工具前缀。切换到其他协议时，已完成的跨轮异步调用与结果按原位置转为历史正文并保留附件，遵守目标协议的配对要求；历史消息与图片顺序不变。

“运行命令”已有受管后台会话：长命令启动后返回会话 ID，后续通过进程会话工具读取或停止。终端命令的后台任务及完成通知继续沿用现有功能。

通过 LLMBridge 使用时，将模型端点配置为 `responses_native`，并填写支持 WebSocket 的 Responses 上游地址。Bridge 与独立 Codex 代理均需更新到包含原生 WebSocket 转发的版本。
