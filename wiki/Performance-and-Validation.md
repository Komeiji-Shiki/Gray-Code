# 性能优化与架构设计

[返回目录](Home.md)

为了在长对话、超大代码仓库以及高频工具调用场景下依然保持轻快流畅，GrayCode 在架构层面进行了多维度的性能优化。

---

## 1. 核心性能优化维度

### 1.1 文件树与界面虚拟化渲染
- **问题**：大型代码仓库动辄包含数万个文件与深层目录，全量 DOM 渲染会导致界面卡顿、内存暴涨。
- **方案**：左侧文件树与长消息列表限制挂载的节点数量。聊天窗口最多渲染 200 行，本地已加载的历史按 40 行逐步展开；已加载分页用尽后再读取下一页，定位后的双向阅读保持重叠锚点。耗时仍受单条消息内容、设备和浏览器影响。

### 1.2 增量历史游标同步
- **问题**：长会话包含数千条消息与多模态图片，若每次交互都全量读取和解析整个对话历史，会导致严重的 CPU 与 IPC 瓶颈。
- **方案**：采用增量版本游标（Incremental History Cursor）。在会话未发生分支分叉时，仅同步最新追加的消息增量；具体延迟取决于消息体积、存储设备和运行负载。

### 1.3 请求快照内容寻址去重（CAS）
- **问题**：多轮工具调用或长上下文对话中，重复的系统提示词、工具声明与历史图片会大量占用磁盘空间。
- **方案**：底层存储对消息快照和多模态附件采用不可变哈希去重，相同内容复用存储。节省比例取决于历史中重复内容的占比；测量时需要同时统计 SQLite 与外部内容文件。

### 1.4 按需依赖加载（Lazy Loading）
- **问题**：全量加载语法高亮器、KaTeX 公式渲染引擎及庞大工具库会显著拖慢工作台启动速度。
- **方案**：采用按需动态导入。只有当消息中实际出现代码块或数学公式时，才动态加载对应的解析库，显著降低首次加载的 JavaScript 体积与启动耗时。

### 1.5 运行时配置按需读取
账号、工作区、渠道、语言服务和调试器查询只复制所需字段或记录；设置编辑仍使用包含版本号的完整快照。运行时每次读取当前已提交配置，返回值保持独立副本，撤权和保存失败均沿用原来的事务规则。默认智能体读取工具名称时直接使用注册表中的名称列表，完整声明供目录和模型请求使用。

### 1.6 子代理监视器的楼层读取
楼层定位复用最近一次窗口已确认的历史前缀，翻页时不重复读取整段历史的标记，追加和局部修改只处理变化部分。缓存只保留最近一个窗口的元数据，存储回收和备份恢复会清除读取快照。消息正文仍按页读取，工具载荷和附件不参与楼层计算。

### 1.7 临时预览回收
文本与附件预览沿用十分钟有效期，通过一个计时器清理最近到期的内容，闲置时也会释放缓存引用。较新图片组继续保留原顺序与有效期；关闭最后一项或退出应用会撤销计时器。预览不写入会话，原有组数和总长度限制保持不变。

### 1.8 文档工具按需读取历史
只读文档校验没有使用对话状态时，不恢复消息正文和附件；普通任务启动也先检查文档确认元数据。写入工具在操作开始时取得元数据和历史版本，只有实际请求历史时才读取正文，仍保留版本冲突保护。同一工具调用复用首次读取的文档内容，写入前重新检查文件当前版本。普通文件事务、当前会话的模式与技能配置、迁移后的归属保存也只读取元数据和版本。

---

### 1.9 流式显示与子代理监视器

主聊天复用未变化的消息行、工具声明与净化后的历史片段，活动正文与思考尾段由 CharFlow 驱动显示。子代理监视器也使用同一显示层，但独立维护显示快照；暂停、切换历史和权威正文改写时恢复真实内容。监视器保留已加载数据，最多挂载 200 条消息，双向移动窗口时根据持久消息身份恢复位置。同帧片段合并更新，工具响应、楼层和固定历史前缀按变化范围复用。

打开会话后的存档摘要与分支预览按明确的对话 ID 独立读取，不占用客户端交互队列，后续恢复、切换与发送可以继续处理。同一对话连续刷新时仅接收最新请求的结果，旧请求也不会提前结束较新分支查询的加载状态。存档元数据仍逐条读取并复用版本缓存，让其他请求有机会进入存储线程。分支预览目前仍会恢复完整历史，超大正文与多模态历史的复制成本仍有优化空间。

### 1.10 工作台与搜索结果

桌面工作台共用一个可见 Monaco 编辑器，各文档模型分别保存撤销、阅读位置、语言服务和断点。批量替换直接操作文档模型。差异列表只读取摘要，选中后再加载原文与提案。项目搜索和工具搜索分别采用固定行高与实际测量高度的显示窗口，结果选择保留在完整数据中，不随行卸载而丢失。

### 1.11 请求存档与缓存一致性

请求快照继续保存实际发送内容。存储线程比较完整条目内容，复用未变化消息与工具的已编码对象引用；缓存有条数和持有体积限制，直接持有线程收到的私有副本。缓存暂存项仅在最外层存储操作成功后发布，失败时丢弃，回收时清除，不在每次命中时查询对象是否存在。完整快照仍经过跨线程传输，内容比较本身仍有成本。单块对象读取、历史替换的首个差异和用量投影减少重复缓冲或正文恢复，不改变原数据格式；部分输出需要统计正文时继续使用原有字段投影读取。

对话元数据缓存使用实际存储写入推进的进程内版本，覆盖创建、更新、删除和备份合并。迟到读取不能填入新版本缓存。桌宠资源采用有界缓存，读取共享定义，标注时才复制，打包只读取一次元数据。屏幕感知历史缓存由服务实例持有，最近记录由数据库直接倒序取 20 条，相关会话用量沿现有令牌增量读取。

用量估算复用不可变工具目录的序列化结果和完整固定前缀计数，但保留原来的分词器与拼接边界，不直接使用上下文预算的数值。提示词每轮读取当前宿主内容，未保留需要先生成正文才能计算键的静态缓存。宿主请求准备仅解除响应式代理，普通兄弟数据和附件可以复用，不进行整根 JSON 转换或克隆失败重试；最终 IPC 克隆或 Web 序列化仍然存在。

## 2. 检索与向量索引设计

- **分层过滤与精确排序**：向量检索与关键词混合检索采用多线程并行处理，在保证排序精度的同时不阻塞主界面的渲染与读写。
- **智能缓存**：记忆向量化与文本嵌入在计算过程中自动复用已计算缓存，避免重复文本多次请求嵌入模型产生额外费用。

## 3. 性能验证

2026-10-17 使用 `npm run build:desktop:trial` 编译当前源码，再运行现有 `node scripts/renderer-performance.cjs --only`。环境为 Windows x64、Intel Core i5-14600K、64 GiB 内存、Electron 44.5.1、Node.js 24.21.0；独立数据目录包含 1,000／5,000 条合成消息，流式输出来自本地 SSE 夹具。

| 本次单轮测量 | 结果 |
| --- | ---: |
| 加载桌面入口到首次输入框挂载 | 1,126 ms |
| 已配置界面重载到输入框挂载 | 114 ms |
| 打开 1,000 条历史到最新消息显示 | 139 ms |
| 打开 5,000 条历史到最新消息显示 | 248 ms |
| 两组流式滚动的帧耗时 P95／P99 | 16.8／16.8 ms |
| 两组采样内超过 50 ms 的长任务 | 0 |
| 两组采样内消息节点峰值 | 40 |

每组帧统计采样 180 帧，基准退出成功，未记录到渲染器错误。首次输入框计时不包含 Electron 进程启动，挂载不等于启动动画完全结束；历史计时止于正文出现，不包含随后完成的分支预览。数据来自一次合成夹具运行，没有测量真实用户库、系统冷缓存、远程网络或安装包。此次未运行全量测试、全仓类型检查或完整桌面冒烟；快速编译和性能基准不能替代这些验证。

本轮构建资源报告中，中文外壳启动需要约 327 KB JavaScript，聊天启动约 1.36 MB（含必需的动态应用模块与当前语言包，均为压缩代码的未 gzip 体积）。后续首屏优化应按实际依赖图继续拆分非必需模块，并用相同计时边界测量收益。

性能测量后补充的请求顺序约束由四项定向用例验证：分支倒序回执与加载状态、存档倒序回执、工作台未打开时的保存退出回执，以及后台查询挂起时客户端交互仍可完成。四项均通过，没有再次运行性能基准。

此前 2026-10 的一轮审查记录采用源码走查和对应的定向检查，覆盖历史窗口、监视器增量与平滑显示、工作台模型生命周期、搜索选择与位置、元数据缓存、请求存档、提示词及屏幕感知记录，语言同步校验覆盖三种语言的共享词条。该轮当时尚未进行完整桌面构建、实际 Electron/Monaco 交互验收或新的性能基准；下方更早的测量应按各自日期和条件理解。

2026-09-28 在 Windows x64、Node.js 22.18.0 下，以 1,201 条消息、12 个各 32 KiB 的附件测量无文档确认请求的启动检查。预热后进行三轮、每轮八次调用，平均单次耗时的中位数由 15.524 ms 降到 0.045 ms，历史版本与附件保持一致。该数据只衡量文档确认检查，不包含模型请求、其他启动步骤或界面渲染。

2026-09-28 在 Windows x64、Node.js 22.18.0 下，以 4,096 条合成消息测量监视器楼层窗口。每页读取 20 条正文，预热后进行 3 轮、每轮 6 页测量，按每轮平均单页耗时取中位数：由 38.017 ms 降到 0.368 ms。另一次追加后的窗口读取由 38.317 ms 降到 0.642 ms。前后楼层列表和正文一致；测量包含存储线程通信及页面正文读取，不包含界面渲染。删除、跨段修改、分支切换、回收和附件投影另由回归覆盖。

2026-09-28 在 Windows x64、Node.js 22.18.0 下，以 48 个渠道、每个渠道 128 个模型选项构建合成配置。预热后进行 5 轮测量，每轮调用账号查询 100 次，中位数由 327.767 ms 降到 0.150 ms。该数据只衡量配置读取路径，不包含网络、模型生成或界面渲染；目录较小时的收益会不同。回归覆盖返回对象隔离、撤权立即生效、过期草稿拒绝，以及真实语言服务、调试和桌面流程。

2026-09-26 的搜索修复保留 8 个文件的并发预取，消费完一个文件后立即解除对其全文的引用。此前完成的 Promise 一直保留在数组中，扫描过的全文会累计到搜索结束。

同机 Node.js 22.18.0、Windows x64 合成对照：256 个文件，每个 128 KiB，使用不能走全文快速拒绝的零命中正则 `/(?<!x)needle/gm`，每 32 个文件让出事件循环、执行 GC 并采样堆内存。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 采样峰值堆内存 | 42.34 MiB | 5.40 MiB |
| 相对启动基线增加的堆内存 | 38.35 MiB | 1.41 MiB |
| 匹配数 / 跳过文件数 | 0 / 0 | 0 / 0 |

这些数据反映该工作负载的保留对象，未包含 Electron、原生内存或真实磁盘延迟。结果顺序、输出预算、文件排除及提前结束后的读取回收由搜索回归测试覆盖。

运行记录合并在同一 Node.js 版本下使用 5,000 条历史事件，再依次追加 1,000 条事件。5 次合成测量的中位数从 312.245 ms 降至 0.093 ms；单次追加读取历史 `sequence` 的次数从 14,999 次降至 1 次。该数据只衡量有序追加函数，不包含 Vue 渲染和 IPC，不等同于界面帧率。

同日追加检查发现，旧记忆扫描每页固定申请 16 MiB 缓冲区，到达 EOF 还会再次申请。改为按当前文件大小分配、逐页复用后，4 条记忆连续读取 50 次的本机一次合成对照中，累计 `Buffer.alloc` 申请量由 1,600.13 MiB 降至 0.91 MiB，耗时由 193.46 ms 降至 20.13 ms，结果一致。这是累计申请量，不是峰值内存；耗时来自一次对照，不能视为所有资料库的速度保证。

存储基准使用 `npm run benchmark:platform`：生成 10,000 条合成消息、重复附件和 100 个分支，输出预热分页耗时、校验结果、存储大小及测量限制。NDJSON 对照用于比较序列化体积，不代表旧适配器运行耗时。

界面组件回归用于验证请求次数、渲染窗口和异步竞态；实际桌面交互另用隔离数据目录与本地合成模型验收。外部模型、Bot 和真实用户数据的效果需要独立验证，不能从本地夹具推定。

2026-09-26 的实际桌面验收使用 Electron 44.2.0 / Node 24.20.0，覆盖发送、模型工具循环、提问与拒绝确认、重生成与分支切换、设置草稿保存、HTML预览和图片组切换。1,250 条合成历史从中段连续滚动至真实尾部，消息节点始终不超过 200，连续定位保留最新目标，验收未记录到前端错误。`scripts/smoke-desktop.cjs` 将应用配置、旧设置迁移来源和文档工作区同时隔离到临时目录。

追加修复后再次构建并执行同一实际桌面流程。输入框实测行高 19.5px，两行正文连同 16px 内边距和 2px 边框完整显示在 57px 高度内，四行输入展开到 96px。后端 3,374 项串行句柄追踪通过并正常退出，未报告未关闭句柄。

## 桌面交互专项回归（2026-09）

`editorPendingWork` 使用受控慢宿主验证待发送修改的合并：100 次连续输入在队列尚未执行时只发送一次最新全文。这个数字仅描述该夹具；实际输入间隔、宿主延迟和保存操作会改变请求数。待发送任务和保存/关闭屏障分开，保持版本与顺序语义。

Markdown 完成态 HTML 使用跨消息共享的 128 条、8 MiB LRU；图片缓存和高亮缓存继续使用各自预算。切换工作区时同时失效图片、文件存在性与完成态 HTML，旧工作区尚在执行的异步任务不得回填缓存。文件变动通知合并 150 ms 后触发失效。
文件变动现在按相对路径与绝对路径通知相关渲染器，无关消息保持原结果；重连和工作区切换仍整体失效。图片读取在所有消息间共享四路并发，同一世代的相同路径复用请求，过期排队项跳过，屏幕内图片优先。四路是同时进行的读取数，不限制图片总数或模型附件数。

低频配置面板与首次打开前的终端按需加载；侧栏按一次分组生成工作区映射，并保留未识别工作区的历史对话入口。后台空闲检查与更新状态轮询均保持单飞请求，更新面板隐藏时暂停轮询。

验证入口：`npm run typecheck:all`、`npm run test:frontend`、`npm run test:platform`、`npm run build:desktop`。Windows CI 的 `scripts/smoke-desktop.cjs` 会点击真实品牌退出对话框，检查默认取消焦点、重复退出互斥和清理失败重试，并保存退出确认截图。安装器原生部署、更新中断和回退仍需在隔离 Windows 环境验收。

### 后续审计的依赖与行为预算

编辑器维持全部编辑贡献和语法注册，TypeScript、CSS、HTML、JSON 的浏览器语言服务按当前语言加载，工作区 LSP 继续负责已有的诊断和补全。主线程的 Monaco 相关块由 PR #43 的 4,034,590 字节降到约 3,994,561 字节，变化约 1%；这不代表完整编辑器首次打开快了同样比例。

`npm run build:desktop` 生成 Vite manifest，并运行 `scripts/renderer-budget.mjs`。报告保存在 `.tmp/renderer-budget.json`，分别列出入口静态依赖、动态面板的静态依赖、主线程大块与 worker。外壳主线程单块上限维持审计前的 4,034,590 字节，聊天为 1,400,000 字节；worker 独立使用 7,100,000 字节预算。Vite 原有的 500 kB 警告保留。入口引导块并不包含随后动态导入的 App，报告中的动态视图依赖必须一起查看。

长对话测量用 `node scripts/renderer-performance.cjs`，只跑测量用 `node scripts/renderer-performance.cjs --only`。脚本先在独立数据目录准备 1,000 / 5,000 条合成历史，关闭准备数据的核心后启动 Electron，保留单实例锁。正文混合公式、Mermaid、长代码块和普通文字，并使用本机 SSE 端点边输出边滚动。结果记录首次打开时间、180 个帧间隔的 P50/P95/P99、长任务和峰值挂载消息数；输出位于 `.tmp/desktop-smoke-renderer-*/renderer-performance.json`。这是单机离屏 Chromium 基线，物理显示器刷新率、屏幕阅读器和真实远端磁盘仍需另外验收。

2026-09-29 本机 Electron 44.2.0 的合成基线：1,000 条首次显示 415 ms，5,000 条 783 ms；两者帧间隔 P95 约 16.8 ms，峰值挂载消息均为 40，采样期间未记录到长任务。每种场景采样 180 帧，页面错误列表为空；这些结果不代表其他设备、远程宿主或无限历史规模的保证。

同日继续检查发现，虚拟窗口移动时会深度遍历整份标记并重新生成坐标；滑块变化还会重复写入未改变的标记样式。现在按标记数据、消息总数与轨道高度缓存投影，并复用稳定标记的渲染结果。均匀取样上限仍为 2,000，点击使用原始消息索引，标记内容或外观变化时正常更新。相关回归覆盖重复读取和样式写入、点击定位、长消息贴底与历史锚点。

修复后的同机离屏复测带 CPU 采样：1,000 / 5,000 条首次显示约 198 / 652 ms，帧间隔 P95 均约 16.8 ms，峰值挂载消息均为 40，采样期间没有长任务或页面错误。这组结果确认交互和挂载边界保持稳定；首次打开耗时有波动，不能据此推断启动速度改善。此前一次无剖析测量出现过单个 212 ms 长任务，后续两次剖析未重现，保留为测量波动记录。

| 组件 | 状态或计算的归属 | 清理与回归边界 |
| --- | --- | --- |
| SubAgentMonitor | `monitorLiveReplay` 持有每个任务的片段缓存，`useMonitorControls` 持有控制回执与计时器 | 版本匹配、迟到事件、同任务重连、停止和历史窗口 |
