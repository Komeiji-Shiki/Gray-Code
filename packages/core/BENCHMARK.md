# 首次存储基准

执行日期：2026-09-07。环境：Windows x64、Node 22.18.0、SQLite 3.53.4；本地执行 `npm run benchmark:platform`。脚本仅生成并删除自身的临时样本，结果写入 `.tmp/platform-benchmark-latest.json`。

样本包含 10,000 条带不同文本和稳定 ID 的消息，其中 100 条重复引用同一份 128 KiB 二进制附件。NDJSON 按 200 条消息分段；新存储按 128 条批量提交，保持 `synchronous=FULL`。随后创建 100 个共享前 9,000 条消息的分叉。

| 指标 | 本次实测 |
| --- | ---: |
| NDJSON、索引与元数据的文件总长度 | 26,597,356 bytes（25.37 MiB） |
| 新存储回收、WAL checkpoint 后的文件总长度 | 14,778,368 bytes（14.09 MiB） |
| 单会话文件长度减少 | 44.44% |
| 批量写入 10,000 条消息 | 975.83 ms |
| 读取末尾 50 条，30 次热缓存采样的中位数 | 0.87 ms |
| 读取末尾 50 条，热缓存 p95 | 1.56 ms |
| 创建 100 个共享前缀的分叉 | 131.25 ms |
| 100 个分叉在 checkpoint 后新增文件长度 | 851,968 bytes（0.81 MiB） |
| 完整性校验 | 10,102 个对象通过，无问题 |

文件长度统计包含 SQLite 和外部对象文件；不等同于文件系统簇分配后的实际磁盘占用。NDJSON 仅作为序列化空间基线，没有测量旧适配器的完整读写延迟，也没有将理论全量复制大小当作实测分叉对照。

这是可复现的单次合成工作负载，重复附件有利于去重结果。它不能证明所有真实历史都有相同节省比例，热缓存读取也不能代表冷启动。尚未覆盖小消息占绝大多数、大型独占媒体、长期修改产生的空闲页、多设备并发、断电或 Electron 打包；因此当前保留压缩阈值，后续用代表性数据再决定是否调整。
